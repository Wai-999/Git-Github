Step 2 · The problem

Everyone has lived this nightmare.

You're working on something important. You save a copy before making big changes. Then another. A week later your folder looks like this:

Same work. One is chaos; the other is a history you can walk through.

The copying approach fails in three ways: you can't tell what changed between two files, you can't tell why anyone changed it, and if two people edit at once, somebody's work gets overwritten.

This is the entire reason Git exists.

Not to be complicated — to make that folder impossible.

Step 3 · The concept

Version control is an undo button for your whole project.

Your text editor lets you undo the last few things you typed. Version control does the same thing, but for every file in your project, going back forever, with a note attached to each point explaining what changed and who did it.

Game metaphor

Think of save points. You play for a while, reach somewhere good, and hit Save. If the next section goes badly, you load your save and try again. Version control is that — for your work.

What it gives you

⏪

Go back safely

Broke something? Return to any earlier point in seconds.

🔍

See what changed

Compare any two moments, line by line.

🤝

Work together

Several people edit the same project without overwriting each other.

🧪

Try wild ideas

Experiment freely, knowing the working version is untouched.

Why isn't "save a copy in a new folder" good enough?

Step 4 · Two different things

Git and GitHub are not the same thing.

Almost every beginner mixes these up, so let's settle it now — it takes ten seconds.

📷

Git = the camera

A free program on your computer. It takes the snapshots and keeps your history. Works with no internet at all.

📱

GitHub = the photo app

A website where you upload those snapshots so others can see them, comment, and contribute. Optional — but it's where teamwork happens.

Game metaphor

Git is your console saving the game to its own memory. GitHub is the cloud save — your friends can load your world, play in it, and send their progress back to you.

Two consequences worth knowing: you can use Git completely alone forever and never touch GitHub — and GitHub isn't the only option (GitLab and Bitbucket do the same job).

Your internet goes down. Can you still save your work with Git?

Step 5 · The black window

Meet the terminal. It's friendlier than it looks.

Git is usually operated by typing, in a program called the terminal. If that sounds intimidating, here's the reframe: it's just a way of asking your computer to do things with words instead of clicks.

Think of it as

Walking through your computer's folders on foot. Instead of double-clicking a folder to open it, you say "go in there". Instead of looking at icons, you ask "what's in this room?"

Open it

🍎

On a Mac

Press ⌘ + Space, type Terminal, press Enter.

🪟

On Windows

You'll install Git Bash in the next step — it comes with Git and gives you the same commands as a Mac.

The only three commands you need today

terminal
pwd          # "where am I standing?"
/Users/you

ls           # "what's in this room?"
Desktop  Documents  Downloads  Pictures

cd Documents # "walk into Documents"
cd ..        # "walk back out"
Two habits that make this painless

Press Tab while typing a folder name and the computer finishes it for you — no typos. Press ↑ to bring back the last command you ran.

Can I break something?

Not with these. pwd, ls and cd only look and walk around — they change nothing. Explore freely.

Step 6 · Setup (once, forever)

Install Git and tell it your name.

This is the only installation in the whole course, and you'll never repeat it on this computer.

1 · Install

🍎

Mac

Open Terminal and type git --version. If it prints a number, you already have it. If not, it will offer to install — say yes.

🪟

Windows

Go to git-scm.com/download/win, run the installer, keep clicking Next. Then open Git Bash from your Start menu.

2 · Sign your work

Every save point gets stamped with your name, so teammates know who did what. Type these two lines once:

terminal
git config --global user.name "Your Name"
git config --global user.email "you@example.com"
That's the whole setup.

Nothing else to configure, ever. From here on it's all doing.

Step 7 · Create the world

Turn a folder into a project Git watches.

Let's make a real project. Type along — this takes 30 seconds.

terminal
cd Documents           # walk into Documents
mkdir my-first-project # build a new folder
cd my-first-project    # step inside it
git init               # ✨ Git starts watching this folder
Initialized empty Git repository in .../my-first-project/.git/

That folder is now a repository — usually shortened to "repo". It's an ordinary folder plus a hidden .git folder where Git stores every save point you'll ever make.

Game metaphor

git init is starting a new game world. Nothing has been saved yet, but the game now has a memory card to save to.

see it for yourself
ls -a       # -a shows hidden things
.   ..   .git       # ← there it is: Git's memory
Don't touch .git

You never need to open it. Just know that deleting it would erase your history while leaving your files alone.

Step 8 · The heart of Git

Make your first save point.

Saving in Git happens in two moves, not one — and that surprises everybody at first. You first choose what to save, then you save it with a note.

terminal
echo "Hello Git" > notes.txt   # create a file with some text

git status                     # always start here — Git tells you what it sees
Untracked files:  notes.txt

git add notes.txt              # put it in the waiting tray
git commit -m "Add my notes"   # save it, with a note explaining why
[main a1b2c3d] Add my notes

🎉 That's your first commit. That short code a1b2c3d is its permanent name — you could return to this exact moment years from now.

Try it — click through the cycle

Click “Edit a file” to begin.

Write notes your future self will thank you for

"Fix crash when the file is empty" is useful. "update", "stuff", "asdf" are not. You'll be reading these later, promise.

Step 9 · Looking back

Read your project's story.

Make a few more save points — change the file, git add, git commit, repeat — then look at what you've built:

terminal
git log --oneline
c3d4e5f  Add a second page
b2c3d4e  Fix the spelling in the title
a1b2c3d  Add my notes

Read it bottom to top and it's the story of your project. Three commands cover almost everything you'll want to know:

📋

git status

"What's changed right now?" Run it constantly — it's your compass.

📜

git log

"What have I saved so far?" Your list of save points.

🔎

git diff

"What exactly did I change since the last save?" Line by line.

The rhythm you'll repeat forever

edit → git status → git add → git commit. Do it after every small piece of work that works — not once at the end of the day.

Step 10 · The superpower

Try risky things without any risk.

You want to redesign your whole page, but you're not sure it'll work. You don't want to ruin the version that currently works fine. So you make a branch.

Game metaphor

A branch is a second save slot. You copy your progress into it and attempt the hard boss fight there. If it goes badly, delete the slot — your main playthrough never knew. If it goes well, bring it into the main game.

Two versions of your project exist at once. Switching between them takes a split second.
terminal
git switch -c my-experiment   # create the second slot and enter it
# …change whatever you like, commit as usual…

git switch main               # hop back — your experiment vanishes from view
git switch my-experiment      # …and reappears. Nothing was lost.

git switch main
git merge my-experiment       # it worked! bring it into the main version
git branch -d my-experiment   # tidy up
What if two people changed the same line?

Git stops and asks you to choose — that's a merge conflict. It looks scary, it isn't: you open the file, pick what the line should say, then git add and git commit. That's the whole fix, and every professional does it weekly.

Check yourself

Your experiment turned out badly. What happens to main?

Step 11 · Into the cloud

Put your project on GitHub.

So far everything lives on your computer alone. Uploading it to GitHub gives you a backup, a link you can share, and the ability to work with other people.

  1. Create a free account at github.com.
  2. Click + → New repository. Give it a name. Don't tick any of the extra options. Click Create.
  3. GitHub shows you a page of commands — you only need these:
terminal
git remote add origin https://github.com/YOU/my-first-project.git
git push -u origin main
* [new branch]  main -> main

Refresh the GitHub page — your files are there, with your commit messages next to them. From now on, uploading is a single word:

the two words you'll use daily
git push    # upload my save points
git pull    # download everyone else's
Game metaphor

push = upload my save to the cloud. pull = download my friends' progress. Start every session with a pull, so you're building on the latest world rather than an old one.

It asks for a password — and rejects it?

GitHub doesn't accept account passwords for uploads. Go to Settings → Developer settings → Personal access tokens, create one, and paste that instead. Your computer remembers it afterwards.

Step 12 · Teamwork

How real teams actually work.

Here's the surprise: on professional teams, nobody edits the main version directly. Everyone proposes changes and someone else looks before it goes in. That single habit is what keeps large projects from falling apart.

This loop runs thousands of times a day at every software company on earth.

That third step — "ask for review" — has a name: a pull request. Despite the confusing name, it simply means: "Here's what I changed. Please look before it goes in." Your teammates read it, leave comments, automated tests run, and then someone clicks Merge.

Game metaphor

A pull request is showing your quest to the guild leader before it becomes part of the shared world. Comments are their feedback; merging is their approval.

Contributing to someone else's project

If you don't have permission to change a project, you fork it — GitHub makes you your own copy — then send a pull request from your copy. That's how millions of strangers safely build open-source software together.

Step 13 · Don't panic

Three fixes cover almost every mistake.

Beginners freeze when something breaks. Skip that phase — here's the only question you need to ask: has anyone else seen it yet?

What went wrong? Click one
The one rule to remember

If it's still only on your computer, you can rewrite it freely. If you already pushed it, use git revert — it undoes the change by adding a new save point rather than erasing history, so nobody else's copy breaks.

Git very rarely loses committed work

Once you've committed something, it's extremely hard to truly destroy — git reflog can usually find it. That's the deeper reason to commit often: committed work is protected work.
