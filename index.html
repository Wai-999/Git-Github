1What Is Version Control?

In plain English

In one sentence: version control is an unlimited undo button for a whole project — one that also remembers who changed what, and why. Instead of keeping report_final_v2_REAL.docx, you keep one file with a complete, labelled history behind it.

A Version Control System (VCS) is software that records changes to a file or set of files over time so that you can recall specific versions later. Think of it as a time machine for your project: every meaningful change is saved as a snapshot, and you can rewind to any of them at any moment.

With a VCS you can:

⏪

Revert

Roll individual files — or the entire project — back to any previous state when something breaks.

🔍

Compare

See exactly what changed between versions, line by line, and when.

👤

Attribute

Know who last modified something that's causing a problem, and why (via the commit message).

🤝

Collaborate

Let many people work on the same files in parallel without overwriting each other's work.

🧪

Experiment safely

Try risky ideas on a separate branch. If they fail, throw them away — the main line of work is untouched.

💾

Back up

Every clone of a distributed repository is a full backup of the entire project history.

The problem it solvesWithout version control, people resort to copying folders: project_final, project_final_v2, project_FINAL_really… This is error-prone: it's easy to overwrite the wrong file, impossible to see what changed, and hopeless for teams. A VCS replaces all of that with one clean, complete, searchable history.

2The Three Types of Version Control Systems

In plain English

The short version: version control had three generations. First it worked on one computer only (no teamwork). Then everything lived on one central server — teamwork became possible, but if the server went down, everyone stopped. Today everyone carries a full copy of the project, so nothing can stop you working, and no single crash can lose the history.

Version control evolved through three generations. Understanding this evolution explains why Git works the way it does.

2.1 Local VCS — one machine, one history

The earliest approach (e.g., RCS, 1982) kept a small database of file changes on a single computer. It solved "which version is this?" but nothing else: no collaboration, and one disk failure destroys everything.

Local VCS: versions tracked in a database on one machine — no collaboration, no redundancy.

2.2 Centralized VCS (CVCS) — one server, many clients

Systems like CVS and Subversion (SVN) put the version database on a central server. Developers "check out" the latest snapshot of files, work, and commit changes back to the server. This enabled team collaboration and gave administrators control — and it was the standard for many years.

Centralized VCS (CVS, SVN): every operation depends on the central server.
Why centralized VCS failed at scale
  • Single point of failure — if the server crashes, nobody can collaborate or commit; if its disk is corrupted without backups, the entire history is lost.
  • No offline work — nearly every operation (commit, log, diff against history) requires a network round-trip.
  • Slow — large projects with long histories became painfully slow to work with.
  • Fragile branching — branches were expensive and merge conflicts were feared, so people avoided branching altogether.

2.3 Distributed VCS (DVCS) — everyone has everything

In a Distributed Version Control System — Git, Mercurial, Bazaar — clients don't just check out the latest snapshot: every clone is a full mirror of the repository, including its complete history. The next section explores what this changes.

3Distributed Version Control, Explained

In plain English

Distributed means: when you download a project, you don't get just the latest files — you get the entire history, every version, every branch. That's why Git is fast (nothing needs the internet) and safe (every teammate's laptop is a complete backup).

Distributed VCS: every clone is a complete backup. Peers can even sync directly with each other.

5Git vs GitHub — Not the Same Thing

In plain English

Easiest way to remember: Git is the app on your computer that saves your progress. GitHub is the website where you upload those saves so others can see them. Git works fine with no internet; GitHub is where teamwork happens. Like a camera (Git) and Instagram (GitHub).

🔧

Git — the tool

An open-source, distributed version control program that runs on your computer. It tracks changes, stores snapshots, manages branches, and merges work. It works perfectly with no internet and no GitHub.

☁️

GitHub — the platform

A cloud service that hosts Git repositories and adds collaboration on top: pull requests, code review, issues, project boards, GitHub Actions (CI/CD), and a public profile that acts as a developer portfolio.

🔗

Together

Git manages history locally; GitHub is the shared meeting point where teams exchange that history, review each other's work, and automate testing and deployment.

AnalogyGit is like a camera that takes snapshots of your project; GitHub is like the shared photo album where everyone publishes, discusses, and organizes those snapshots. Alternatives to GitHub include GitLab and Bitbucket — same Git underneath, different platform features.

6The Command Line — Your Developer Cockpit

In plain English

Don't be scared of the black window. It's just a way of asking your computer to do things by typing instead of clicking. Every command follows the same shape: the verb, then what to do it to — cd projects means "go into projects". Nothing you type here can break your computer, and you can't lose your work by exploring with pwd, ls, and cd.

Before Git makes sense, you need the environment it was born in: the command line. Instead of clicking through windows, you type text commands into a shell — a program that interprets what you type and asks the operating system to do it. Developers rely on it because it is faster (no menu-hunting), scriptable (automate anything you can type), universal (the same commands work on any server in the world), and it's where professional tools — Git included — live first.

Terminal vs shell — two different things

🖥️

Terminal

The window you type into (Terminal.app, Windows Terminal, iTerm2). It just displays text and sends your keystrokes onward.

⚙️

Shell

The interpreter running inside it — bash (Bourne Again Shell, the standard), zsh (macOS default since Catalina, bash-compatible), PowerShell, etc.

📟

Prompt

The text waiting for your input, typically ending in $ (or % in zsh). When you see $ in documentation, it means "type this into a shell" — don't type the $ itself.

Getting a Unix shell on each OS

macOS is Unix-based, so you're ready out of the box. Open Terminal (Cmd+Space → "Terminal"). The default shell is zsh, which runs every bash command in this guide identically. Check yours with echo $SHELL; switch with chsh -s /bin/bash if you prefer bash.

Windows' native CMD and PowerShell use different commands, so use one of these to follow along with Unix commands:

  • Git Bash (recommended for this course) — installed automatically with Git for Windows; gives you a bash shell with all the Unix commands below.
  • WSL (Windows Subsystem for Linux) — a full Linux environment inside Windows: wsl --install in an admin PowerShell.

Open your terminal emulator — bash is almost certainly already your shell. You live here now. 🐧

What are "Unix commands"?A standard vocabulary of small programs — ls, cd, grep… — from the Unix operating system (1970s, Bell Labs) that every Unix-like system (Linux, macOS, Git Bash) shares. Each does one thing well, and they're designed to be combined — the philosophy behind pipes (below). Get help on any command with man ls (manual) or ls --help.

7Navigating the Filesystem

In plain English

Only three commands matter at first: pwd (where am I?), ls (what's here?), cd (go there). That's genuinely enough to move anywhere on your computer. And press Tab constantly — it finishes names for you and prevents typos.

The filesystem is a tree of directories (folders). At any moment your shell is "standing" in one of them — the working directory. Three commands cover 90% of navigation:

pwd — where am I?

terminal
pwd
/Users/wai/projects       # "print working directory" — your current location

ls — what's here?

terminal
ls                # list files and folders in the working directory
ls -l             # long format: permissions, owner, size, modified date
ls -a             # include hidden files (names starting with "." — like .git!)
ls -la            # combine flags: long format + hidden files
ls projects/      # list a different directory without going there
FlagsOptions starting with - modify a command's behavior. -l, -a, -la — most commands accept many; man command lists them all. This is also why you can find .git: it's a hidden directory, visible only with ls -a.

cd — go somewhere

terminal
cd projects       # move into the "projects" folder (relative path)
cd /Users/wai     # jump to an exact location (absolute path, starts with /)
cd ..             # up one level (.. = parent directory)
cd ../..          # up two levels
cd ~              # home directory (~ is shorthand for it)
cd -              # back to wherever you were before

8Creating, Moving & Deleting Files and Directories

Creating

terminal

echo "hello" > hi.txt      # create a file WITH content (more on > soon)

Viewing file contents

terminal
cat notes.txt              # print the whole file
less big.log               # scroll through a large file (q to quit)
head -n 5 data.csv         # first 5 lines
tail -n 5 data.csv         # last 5 lines
wc -l data.csv             # count lines (-w words, -c bytes)

Copying, moving, renaming

terminal
cp notes.txt backup.txt    # copy a file
cp -r src/ src-backup/     # -r (recursive) to copy a directory
mv notes.txt docs/         # move a file into a directory
mv draft.txt final.txt     # mv also RENAMES (move to a new name)

Deleting — with respect

terminal
rm old.txt                 # delete a file
rmdir empty-folder         # delete an EMPTY directory
rm -r old-project          # delete a directory and everything inside
There is no Trash hererm deletes immediately and permanently — no undo, no recycle bin. Be triple-careful with rm -r, and treat rm -rf (force, no prompts) as a chainsaw: read the path twice before pressing Enter. (One more reason to commit to Git often — committed work is recoverable.)

9Power Tools: Pipes, Redirection & Grep

In plain English

The big idea: each command is a tiny tool that does one job. The pipe | is a conveyor belt that feeds one tool's output into the next. So cat log | grep "ERROR" | wc -l reads: pour out the log → keep only error lines → count them. Three simple tools, one useful answer.

This is where the Unix philosophy pays off: small commands become powerful when you connect them.

Standard streams — the plumbing

Every command has three data streams: stdin (input, 0), stdout (normal output, 1), and stderr (error messages, 2). By default stdout/stderr go to your screen — redirection and pipes reroute them.

Redirection — send output to files

terminal
ls -l > listing.txt        # >  write stdout to a file (OVERWRITES it)
echo "new line" >> log.txt # >> append to the end instead
sort < names.txt           # <  feed a file in as stdin
python run.py 2> errors.log# 2> capture only error output
python run.py > out.log 2>&1  # everything (stdout + stderr) into one file

Pipes — chain commands together

The pipe | connects one command's stdout to the next command's stdin — an assembly line for text:

terminal
ls | wc -l                       # how many items in this directory?
cat access.log | grep "404" | wc -l   # how many 404 errors in the log?
sort names.txt | uniq            # sorted, duplicates removed
git log --oneline | head -n 10   # pipes work with Git too!

grep — find anything, anywhere

global regular expression print: searches text for lines matching a pattern. One of the most-used commands in a developer's life:

terminal
grep "error" app.log             # lines containing "error"
grep -i "error" app.log          # -i: case-insensitive (Error, ERROR…)
grep -n "TODO" main.py           # -n: show line numbers
grep -r "import pandas" src/     # -r: search a whole directory tree
grep -v "DEBUG" app.log          # -v: invert — lines NOT matching
grep -c "login" access.log       # -c: just count matches
ls | grep ".ipynb"               # filter any command's output
Why this matters for GitGit is a command-line citizen: git log --oneline | grep "fix" | wc -l counts your bugfix commits. Everything you learned here composes with everything Git does.

11How Git Thinks — The Mental Model

In plain English

The one thing to understand: a commit is a photograph of your entire project at a moment in time, not a list of edits. Each photo is stamped with who took it, when, and a note about why — and it points back to the previous photo. That chain of photos is your history.

Most Git confusion disappears once you internalize four ideas from Pro Git:

6.1 Snapshots, not differences

Older systems (CVS, SVN) store data as a list of file-based changes (deltas). Git instead stores a snapshot of the entire project at every commit — like a miniature filesystem photographed at a moment in time. Unchanged files aren't duplicated; Git just links to the identical file it already stored. This is why branching, merging, and time-travel are so fast in Git.

6.2 Nearly every operation is local

History browsing, diffs, commits, branch switches — all read from your local database, so they feel instantaneous and work offline (on a plane, on a train, off VPN). You only touch the network when you explicitly fetch, pull, or push.

6.3 Integrity: everything is checksummedadvanced

Every object in Git is addressed by the SHA-1 hash of its contents — a 40-character fingerprint like 24b9da6552252987aa493b52f8696cd6d3b00373. You cannot change any file, commit, or byte of history without Git noticing, because the checksum would no longer match. A commit's ID even depends on its parent's ID, so history forms a tamper-evident chain.

6.4 The three states & three areas

Every tracked file is in one of three states, corresponding to three areas of a Git project:

The fundamental Git cycle: modify in the working directory → stage the parts you want → commit a permanent snapshot.
Why a staging area?It lets you craft precise commits. You might edit five files but stage and commit only two of them as one logical change ("fix data loader"), then commit the rest separately ("update README"). Clean, reviewable history comes from this control.

6.5 What a commit actually is

A commit is a small object containing: a pointer to the snapshot (tree) of your project, the author & timestamp, your message, and a pointer to its parent commit(s). Chained together, commits form the project's history graph. A branch is nothing more than a lightweight, movable pointer to one of these commits — which is why creating a branch in Git is instant (it writes a 41-byte file).

Infographic: anatomy of a commit

A branch ("main") is just a pointer to the newest commit; HEAD points to the branch you're on. That's the whole trick.

15Branching & Merging — Git's Superpower

In plain English

Why branches exist: so you can try something risky without endangering the working version. Make a branch, break things freely, and if it doesn't work out, delete it — the main version never knew. If it does work, merge it in.

A branch is a movable pointer to a commit — creating one is instant and free. Branches let you develop features, run experiments, and fix bugs in parallel universes that don't disturb the stable main branch.

Work happens on a branch (C4, C5) while main stays stable; a merge (C7) combines both histories.

Branch commands

terminal
git branch                        # list branches (* = current)
git branch feature-scaling        # create a branch
git switch feature-scaling        # switch to it (modern syntax)
git switch -c experiment-xgboost  # create AND switch in one step
git checkout -b experiment-lstm   # same, classic syntax
git merge feature-scaling         # merge that branch INTO the current one
git branch -d feature-scaling     # delete after merging

How merging works

  • Fast-forward merge: if main hasn't moved since you branched, Git simply slides the pointer forward. No new commit needed.
  • Three-way merge: if both branches advanced, Git compares both tips with their common ancestor and creates a merge commit with two parents.

Merge conflicts — don't panic

If two branches change the same lines of the same file, Git can't decide for you. It pauses the merge and marks the file:

conflicted file
<<<<<<< HEAD
learning_rate = 0.01        # your version (current branch)
=======
learning_rate = 0.001       # their version (incoming branch)
>>>>>>> experiment-lstm
  1. Open the file, decide what the final code should be, delete the <<<<<<< ======= >>>>>>> markers.
  2. git add the resolved file.
  3. git commit to complete the merge.

Rebase (the other way to integrate)advanced

git rebase main replays your branch's commits on top of main, producing a straight-line history instead of a merge commit. Cleaner to read — but it rewrites commits.

The golden rule of rebasingNever rebase (or otherwise rewrite) commits that you've already pushed and others may have based work on. Rebase your own local work freely; leave shared history alone.

Infographic: merge vs rebase — the eternal debate

Real-world convention: rebase your own unpushed work to keep it tidy; merge (via pull request) to combine shared work.

terminal
git tag -a v1.0 -m "Baseline model: 87% accuracy"

Tags are permanent bookmarks — ideal for releases and for marking ML experiment milestones ("the model we showed the client").

16Remotes — Connecting to GitHub

In plain English

Remote just means "the copy on the internet". push = upload my saves. pull = download everyone else's. Start each work session with a pull, so you're building on the latest version rather than an old one.

A remote is a named reference to another copy of your repository, usually on GitHub. The default name is origin.

11.1 Create the GitHub repository

  1. Sign in at github.com → click + → New repository.
  2. Enter a name and description; choose Public (portfolio) or Private.
  3. Click Create repository.

11.2 Link your local repo and push

terminal
git init
git add .
git commit -m "Initial commit"
git branch -M main
git remote add origin https://github.com/username/repo.git
git push -u origin main       # -u remembers the pairing; later just "git push"

11.3 Staying in sync

terminal
git remote -v        # list remotes
git fetch origin     # download new history — does NOT touch your files
git merge origin/main# integrate what was fetched
git pull             # fetch + merge in one command
git push             # upload your commits
fetch vs pullgit fetch is always safe — it only downloads and lets you inspect before integrating. git pull = fetch + merge immediately. Habit for teams: pull before you start working each day, and before every push.

The very first download: copies the entire repository — every file, branch, and commit — onto your machine and wires up origin automatically. You clone once per project, ever.

🔭

git fetch — look

Downloads new commits from the remote without touching your files. Safe at any moment. Inspect what arrived with git log origin/main, integrate when ready.

🔄

git pull — sync

fetch + merge in one step: downloads AND updates your working files. The everyday habit — start each session with a pull so you build on the team's latest work.

17Connecting to GitHub: HTTPS vs SSH

In plain English

Why this exists: GitHub needs proof it's really you before accepting uploads. Either you paste a token (a long password Git remembers for you), or you set up an SSH key once — a pair of files where you give GitHub the public half and keep the secret half. After that, uploads just work.

When you push or pull, GitHub must know it's really you. There are two ways to authenticate — both secure, different trade-offs:

🔑

HTTPS + token

URLs like https://github.com/user/repo.git. You authenticate with a Personal Access Token (PAT) — GitHub no longer accepts account passwords for Git operations. Easiest to start; works through corporate firewalls.

🗝️

SSH keys

URLs like git@github.com:user/repo.git. A cryptographic key pair on your machine proves your identity — no password prompts ever again. The professional default.

Option A — HTTPS setup

  1. GitHub → Settings → Developer settings → Personal access tokens → Generate new token (give it repo scope, set an expiry).
  2. Use it as your password the first time Git asks. Your OS credential manager (Git Credential Manager on Windows, Keychain on macOS) remembers it afterwards.
terminal
git clone https://github.com/username/repo.git
# Username: your GitHub username
# Password: paste the token (NOT your account password)

Option B — SSH setup (once per machine)

terminal
# 1. Generate a modern key pair (press Enter to accept defaults)
ssh-keygen -t ed25519 -C "you@example.com"

# 2. Start the agent and load your private key
eval "$(ssh-agent -s)"
ssh-add ~/.ssh/id_ed25519

# 3. Copy the PUBLIC key…
cat ~/.ssh/id_ed25519.pub

# …and paste it at GitHub → Settings → SSH and GPG keys → New SSH key

# 4. Test the connection
ssh -T git@github.com
Hi username! You've successfully authenticated…
Key hygieneThe .pub file is shareable — that's the public half. The other file (id_ed25519) is your private key: never share it, never commit it, never email it. One key pair per machine is the clean pattern.
Which should you use?Starting out or on a locked-down network → HTTPS. Daily development on your own machine → SSH, set up once and forget passwords forever. You can check which a repo uses with git remote -v and switch anytime with git remote set-url origin <new-url>.

18Collaboration: GitHub Flow, Pull Requests & Issues

In plain English

How teams actually work: nobody edits the shared version directly. You make a branch, do your work, and open a pull request — which is simply saying "here's what I changed, please check it before it goes in". Teammates comment, tests run, then it gets merged. That's it — that's professional software development.

The most widely used team workflow is GitHub Flow — simple, safe, and review-centered:

1
git switch -c feature-xBranch off main for each feature/experiment — never work directly on main
2
commit, commit…Small, focused commits with clear messages
3
git push origin feature-xPublish the branch to GitHub
4
Open Pull RequestPropose merging; teammates review, comment, request changes
5
Merge ✅After approval (and passing tests), merge into main and delete the branch

Pull Requests (PRs)

A PR is a conversation around a proposed change: it shows every commit and line-diff, hosts review comments, runs automated checks, and records the decision. PRs are quality control — bugs get caught before they reach main, and knowledge spreads through review.

GitHub Issues

Issues track bugs, ideas, and tasks. Reference them in commits and PRs ("Fixes #42") and GitHub links — and even auto-closes — them. Labels, milestones, and project boards turn Issues into lightweight project management.

Forking (open-source model)

When you lack write access to a repository, you fork it (your own copy on GitHub), push changes to your fork, and open a PR back to the original. This "integration-manager" workflow is how strangers safely collaborate on open source — a workflow only possible because Git is distributed.

19Under the Hood: HEAD, Diff & Blame

In plain English

Three questions, three commands: "Where am I?" → HEAD. "What did I change?" → git diff. "Who wrote this line and why?" → git blame. Together they let you understand any codebase, including your own from six months ago.

HEAD — "you are here"

HEAD is Git's pointer to whatever you currently have checked out — normally the tip of your current branch. It's literally a tiny file: .git/HEAD, usually containing ref: refs/heads/main. When you commit, the branch moves forward and HEAD rides along; when you switch branches, HEAD is what changes.

terminal
cat .git/HEAD               # see it yourself — just a pointer!
ref: refs/heads/main
git show HEAD               # the commit you're standing on
git show HEAD~1             # its parent (~2 = grandparent, etc.)
Detached HEAD — not as scary as it soundsChecking out a specific commit (git checkout a1b2c3d) points HEAD at a commit instead of a branch. You can look around freely — but commits made here belong to no branch and can be lost. Want to keep work from there? git switch -c rescue-branch. Want out? git switch main.

Diff — see exactly what changed

terminal
git diff                    # working directory vs staging (unstaged edits)
git diff --staged           # staging vs last commit (what will be committed)
git diff HEAD               # everything vs last commit (both of the above)
git diff main feature-x     # compare two branches
git diff HEAD~2 HEAD -- app.py   # how one file changed over 2 commits

Reading diff output: lines starting with - were removed, + were added; the @@ -12,7 +12,9 @@ "hunk header" tells you where in the file you are.

Blame — who changed this line, and why?

Despite the name, git blame isn't about pointing fingers — it's archaeology. For every line of a file it shows the commit, author, and date that last touched it:

terminal
git blame config.py
a1b2c3d (Wai  2026-06-01) MAX_RETRIES = 5
e4f5g6h (Ana  2026-07-12) TIMEOUT = 30      ← who set this? now you know
git blame -L 10,20 config.py  # only lines 10–20
git log -p config.py          # full change history of the file, with diffs

Found the commit that changed the line? git show <commit> reveals its message and full context — usually answering "why is the code like this?" On GitHub, the same view is the Blame button on any file.

#    …edit code…
git diff                          # 3. review your own changes first

20Undoing Things — The Safety Manual

In plain English

Don't memorize these — memorize the question: has anyone else seen it yet? If it's still only on your computer, you can rewrite freely. If you already pushed it, use git revert, which undoes the change by adding a new commit instead of erasing history. And if you truly panic: git reflog — Git almost never loses committed work.

SituationCommandDanger level
Discard edits in a file (back to last commit)git restore file.py⚠️ Edits are gone forever
Unstage a file (keep the edits)git restore --staged file.py✅ Safe
Fix the last commit message / add a forgotten filegit commit --amend⚠️ Rewrites the last commit — only if not pushed
Undo a pushed commit, safelygit revert <commit>✅ Safe — creates a new "opposite" commit, history preserved
Move the branch back, keep changes as uncommittedgit reset <commit>⚠️ Rewrites history
Move back and DELETE all changes sincegit reset --hard <commit>🔥 Destructive — work is discarded
Shelve messy work-in-progress temporarilygit stash → later git stash pop✅ Safe
Find a "lost" commit after a bad resetgit reflog🛟 Your safety net — Git rarely truly loses committed work

Infographic: which undo command do I need?

The decision tree professionals run in their heads before undoing anything.
Rule of thumbOn anything already pushed to a shared branch, use git revert (safe, additive). Reserve reset and --amend for local, unpushed work. If you're stuck mid-disaster, don't guess with --hard — git reflog first.

21.gitignore & Handling Large Files

In plain English

Not everything belongs in a repository. Code: yes. Passwords: never — once committed, they live in the history forever. Huge data files: keep them elsewhere. The .gitignore file is your bouncer at the door — list what Git should ignore, and it will.

14.1 The .gitignore file

Some files should never be tracked: temporary files, credentials, caches, giant data. List patterns in a file named .gitignore at the repo root:

.gitignore (data science example)
# Secrets — NEVER commit these
.env
*.pem
credentials.json

# Python
__pycache__/
*.pyc
venv/

# Jupyter
.ipynb_checkpoints/

# Data & models (too big for Git)
data/raw/
*.csv
*.parquet
models/*.pkl

# OS junk
.DS_Store
Thumbs.db

Ready-made templates for every language live at github.com/github/gitignore.

14.2 Large files & Git LFSadvanced

GitHub blocks files over 100 MB, and Git itself was never designed for huge binary files — every version of a large file bloats every clone. Options, in order of preference:

  • Don't commit big data at all. Keep raw datasets in cloud storage (S3, Drive, a database) and commit the download script plus a small sample.
  • Git LFS (Large File Storage): stores large files outside the normal history and keeps a small pointer in Git:
terminal
git lfs install
git lfs track "*.pkl"
git lfs track "*.h5"
git add .gitattributes      # commit the tracking rules themselves
Quick ruleCode, configs, notebooks, small reference files → Git. Datasets, trained models, media → cloud storage or LFS. Secrets → nowhere near a repository, ever.

Infographic: what belongs in a repository?

✅

Always commit

Source code (.py, .js…) • notebooks (outputs stripped) • requirements.txt / lock files • configs & templates without secrets • README, docs, licenses • tests • .gitignore itself • small reference/sample data

⚠️

Think twice (LFS / cloud)

Trained models (.pkl, .h5) • images & media assets • datasets under ~50 MB you truly need versioned • anything binary that changes often — every version bloats every clone forever

⛔

Never commit

API keys, passwords, tokens, .env files • private keys (.pem, id_ed25519) • customer / personal data • huge raw datasets • __pycache__, venv/, node_modules/ • OS junk (.DS_Store)

22Git for Data Science & ML Projects

In plain English

For data and ML work: commit the recipe, not the ingredients. Code, notebooks, and the list of packages go into Git; giant datasets and trained models live in cloud storage. Then anyone can rebuild your results from scratch.

15.1 Professional project structure

recommended layout
my-ml-project/
├── data/
│   ├── raw/          # untouched source data — never modify (gitignored if large)
│   └── processed/    # cleaned, transformed data ready for analysis
├── notebooks/        # exploration & analysis notebooks
├── src/              # reusable, tested Python modules
├── models/           # trained models (LFS or cloud storage)
├── reports/          # final figures & results
├── requirements.txt  # pinned dependencies for reproducibility
├── .gitignore
└── README.md         # problem, approach, results, how to run

15.2 Branch-based ML experiments

Treat each experiment like a feature: git switch -c experiment-xgboost, iterate, commit results. If the experiment wins, merge it via a pull request; if not, delete the branch — main never saw the mess. Tag milestones (v1.0-baseline, v2.0-tuned) so any reported result can be reproduced from its exact code.

15.3 Jupyter notebooks — the tricky case

Notebooks store code and outputs (images, tables) as JSON, so a tiny code edit can produce a huge, unreadable diff. Two tools fix this:

🧹

nbstripout

Automatically strips output cells before each commit, so Git only tracks the code. pip install nbstripout && nbstripout --install

🔄

Jupytext

Pairs each notebook with a plain .py file that diffs and reviews beautifully. Use both together for clean tracking.

The golden rule for notebooksCommit notebooks with outputs cleared. Restart-and-run-all before committing to make sure the notebook actually executes top to bottom.

15.4 Reproducibility checklist

  • ✅ requirements.txt (or environment.yml) with pinned versions
  • ✅ README that explains the problem, the approach, the results, and exact setup steps
  • ✅ Fixed random seeds recorded in code/config
  • ✅ Data acquisition documented or scripted (where does data/raw come from?)
  • ✅ Anyone should be able to git clone → install → run and get your results

15.5 GitHub as your portfolio

  • 3 strong projects showing different skills: data cleaning, ML modeling, deployment.
  • Crystal-clear READMEs — problem, solution, results, in plain language, with visuals.
  • A green contribution graph — commit regularly; consistency signals discipline.
  • Pinned repositories on your profile act as your professional showcase to employers.

23From Code to Production — Where Git Fits

In professional teams, Git/GitHub is the entry point of a release pipeline that moves software safely through environments (this connects to the Development Environments infographic in your folder):

GitHub Actions (CI/CD) in one glance

A small YAML file in .github/workflows/ tells GitHub to run jobs on every push: run your test suite, lint the code, retrain or validate a model, deploy on merge to main. The loop becomes: Push code → tests run → model/app deploys → you get notified ✅. Benefits: automatic updates, error prevention before users are affected, and total traceability — every production release maps to an exact commit.

Why environments matterEach stage adds a layer of confidence. Staging mirrors production so migrations, configs, and features are validated before real users see them — the closer the mirror, the fewer failures reach production. Git tags + branches are what let teams know exactly which code is in each environment.

24Best Practices & Common Pitfalls

In plain English

If you remember five things: commit small and often · write messages that explain why · branch for anything risky · pull before you push · never commit secrets.

✅

Do

Commit early and often — small, logical units • Write imperative, descriptive messages • Branch for every feature/experiment • Pull before you push • Review via pull requests • Keep main always working • Use .gitignore from day one

❌

Don't

Commit secrets, API keys, or passwords (history remembers forever!) • Commit huge datasets or binaries • Work directly on main in a team • Force-push shared branches • Write messages like "update" / "fix" / "asdf" • Let work sit uncommitted for days

If you ever commit a secretDeleting it in the next commit is NOT enough — it lives in history. Rotate/revoke the credential immediately, then scrub history (e.g., git filter-repo) and force-push with your team's coordination.
The golden rule (from your slides)Branch for every experiment, commit with clear messages, and never push secrets or huge files.

Create an empty repository on github.com (+ → New repository, name it recipe-site, don't add a README), then connect and upload:

  3. Click Create pull request.
  4. Ana reviews it, leaves a comment, you push another commit to the same branch — the PR updates automatically.
  5. She approves. Click Merge pull request → Confirm merge → Delete branch.

git switch main

Scene 7 — The merge conflict (don't skip this)

Meanwhile Ana edited the site title on main… and so did you, on a branch. Both changed the same line:

terminal
git switch -c better-title
# you change the title to "Family Recipes"
git commit -am "Rename site to Family Recipes"

git switch main
git pull                        # Ana's change arrives: she renamed it "Our Kitchen"

CONFLICT (content): Merge conflict in index.html
Automatic merge failed; fix conflicts and then commit the result.

=======
